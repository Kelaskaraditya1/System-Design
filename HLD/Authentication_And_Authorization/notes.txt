                                                                                    USERNAME AND PASSWORD AUTHENTICATION
=====================================================================================================================================================================================================

1) Hashing: Hashing is a operation in which we pass our plain text to a hashing function and it returns a hash value

for eg: if we want to hash our pasword than the hashing function could be, the ascii(char+1), means replace every charecter in the password with it's equivalent (ascii+1)th charecter

2) Salting: Hashing can be predictable like there is a rainbow table which has the plain text for most significant hash values.
so we add a random salt to the password so even though 2 users have same password because of salt it becomes different String and generates different hash everytime.
and the hash is also added in the new hashed password so that there is no need of storing salt in a different column

for eg: Hashed password = $2b$12$+[22-character salt]+[31-character hash]

Components: 

1) Servlet Filter chain:

Filter: it is a part which recives the request and inspects or processes it, before it reaches the controller.
it can, intercept/process the request
        modify the request or response
        continute the chain, by passing the request to next Filter
        reject the request and send response to the client.

Security Filter chain is a group of, layers of filters.

2) Authentication Filter: this has various filters reagarding to Authentication.
now since we are dealing with username and password, there is a UsernameAndPasswordAuthenticationFilter which takes username and password and converts them into Authentication attempts
and our /login endpoint should be handled by UsernameAndPasswordAuthenticationFilter

3) AuthenticationManager:

The Authentication Filter points to AuthenticationManager for Authentication.
AuthenticationManager takes the Authentication object and passes it to appropriate Authentication Provider for Authentication.

4) AuthenticationProvider:

AuthenticationProvider is an entity which is responsible for Authentication or it has different Authentication techniques for different types of Authentication
now in case of Username/Password Authentication we use DAOAuthenticationProvider.

5) DAOAuthenticationProvider: DAOAuthenticationProvider requires 2 things for Authentication UserDetailsService and PasswordEncoder.
UserDetailsService is what loads UsersDetails information on the basis of username provided
UsersDetails is a entity which represents users information.

6) SecurityContext: Spring Security has to remember who all are authenticated so it uses SecurityContext to store who all are authenticated.
SecurityContextHolder is what holds SecurityContext.


=====================================================================================================================================================================================================
                                                                                    JWT AUTHENTICATION
=====================================================================================================================================================================================================

We have to provide username and password everytime we have to access any resources, so instead of that once the user is Authenticated for the first time the server gives it a token known as JWT Token.
The Jwt token proves that the user is Authenticated and it is short lived, therefore  we have to keep renewing it using Refresh token, Refresh token has a longer life span as compared to Jwt Token.
The Jwt Token can also store some users information like userId etc it is known as Claims.
Jwt Token has a initiated date and a expiry date, once expire we use the refresh token to generate a new Jwt Token.

representation: 

xxxxx.yyyyy.zzzzz
  ↑      ↑      ↑
Header  Payload Signature

1) Header: This part contains the Signing Algorithm  and the type of token 

  {
  "alg": "RS256",
  "typ": "JWT"
}

2) Payload: This contains the metadata about the token like subject, issuedAt, expiredAt etc

{
  "sub": "user-123",
  "iss": "authentication-service",
  "role": "USER",
  "iat": 1723800000,
  "exp": 1723803600
}

subject : users information, generally username
role: which role is assigned to the user
iss: issued at
exp: expired at

3) Signature: This represents the Digital Signature of combination of Base64 encoded Header, payload and secret key.

signature =Sign(Base64URL(header) + "." + Base64URL(payload), key)
this is digitally signed and not encrypted

final Jwt Token = Base64URL(Header).Base64URL(Payload).Signature

Need of Signature part:
The Signature represents the checksum(wheather or not data is tempared)
the attacker can modify the payload information or the Header information and the modification generates a different signature as compared to original so this difference denotes that there is temper in the token 

Validation: 

The one who is going to recive the Jwt token should have the same secret key as the issuer for verification.
The reciver seprates the Header and Payload and uses Base64 decoder to decode and get the original value.
than it uses that information again to regenerate the signature part using the secret key and compares the signature part of both if same than valid user else invalid
Trust Claims only after succesful validation.

RS250 Algorithm: RS256 is a Asymetric Encryption algorithm.
means it uses 2 keys for encryption and decryption.
The issuer has the private key and it is only with the issuer service which geneares the token and the public kkey is being distributed amongs all the service who are going to consume the jwt token and they use the public key to decode the jwt token.

This is generally used in Microservices architecture where the issuer service possess the private key and the services who are going to  consume the jwt token has the public key.


=====================================================================================================================================================================================================
                                                                                    JWT AUTHENTICATION USING RS256 ALGORITHM
=====================================================================================================================================================================================================

We can implement Jwt Authentication using both Symmetric and Asymmetric cryptography 

1) Symmetric cryptography: which uses same secret key for generating and validation of token (using HMACSha 256)
2) Asymetric cryptography: it uses 2 different key, 1 private and 1 public the private key is used for generating the token and public key which is distributed to all is used for validation (RS256)

RS256: Algorithm 

Implementation steps:

1) generate a public key and private key and store it in res/ using the below commands and run it in git bash.

Public Key: openssl rsa -in private_key.pem -pubout -out public_key.pem
Private Key: openssl genrsa -out private_key.pem 2048

this commands create 2 files which represents the public and private key and place them in res/

2) Autowire the Resource object in jwtService which points to the files in res/

  @Value("classpath:private_key.pem")
    private Resource privateKeyResource;

    @Value("classpath:public_key.pem")
    private Resource publicKeyResource;

than write 2 functions for getting public and private key from the Resource object.

3) than use private key while generating Jwt Token and private key while in the verification part which is written in verifyClaims()
